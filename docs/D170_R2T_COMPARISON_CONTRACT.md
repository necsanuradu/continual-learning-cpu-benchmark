## 3. Algorithm-neutral capability-expansion benchmark (independent public design)

A separate prospective challenge measures whether an evolving system genuinely *acquires new input-dependent capabilities* rather than simply revisiting different goals. Use four independent procedurally generated task families, A→B→C→D, each with a shared simple discrete 4-action interface but increasing observation dimension and additional genuinely necessary channels (e.g. orientation, terrain-cost, dynamic block state, door/key constraints). The split generators must be **family-disjoint**, with TRAIN, DEV and sealed TEST identities; inputs must not contain stage IDs that reveal the desired policy.

Require an independent BFS or Dijkstra oracle depending on task mechanics and costs. Freeze legal transition rules, environments, representations, objectives, seeds, chance baseline, episode cap and uncertainty evaluation before training. Record all previous full-task performance after every stage. Feature expansion must be causally useful: ablate newly added channels and demonstrate a material competence drop on the new family. Architectural growth must be real allocations in the **same evolving lineage** with reproducible hash-linked checkpoint continuity, not newly trained independent models. Some fixed-capacity baselines may not support dynamic dimensions natively: preserve their authentic input schema or document a separately adapted baseline and its parameter allocation. Never assert native compatibility without qualification.

Predeclare success thresholds (e.g. ≥80% out-of-sample success on each acquired task, and a ≤5 percentage-point absolute decline from an earlier qualified checkpoint), report failed stages and uncertainty intervals. Compare growth and retention first; compute efficiency is a secondary conditional comparison after competence is matched. Do not commit any proprietary PathLight implementation, weights or protected performance to this public repository.

## 4. £0 CPU feasibility, explicitly separate from performance evidence

Published CW20, 20 stages × 1,000,000 simulator transitions = 20,000,000 transitions per method/seed; three methods × five common seeds = 300,000,000 transitions *before* evaluation, distillation and retraining. For PackNet published protocol, 1,900,000 configured additional retraining iterations **per seed**. For Nevo, up to 760,000 configured distillation iterations **per seed**. EWC importance additionally draws up to 48,640 example slots per seed across 19 boundaries, each involving expensive Jacobians. No common conversion from these counts into runtime is justified.

Pure non-training GitHub CPU qualification has succeeded previously, but does **not** establish feasibility for full sequential training. An eventual explicitly authorized feasibility pilot would run a small, independently budgeted interval **on authentic original learning paths** and measure simulator steps/second, actual actor/critic update/second, task transition runtime, CPU peak memory, free runner queue and wall-time, checkpoint overhead and artifact storage. A short smoke test, synthetic fixtures or model initialization cannot certify that the full original run fits free-tier allowances. No paid runners, no GPU expenditure.

**Decision:** GO for further source-level audit and non-training harness qualification only. NO-GO for comparative neural training until separate CTO/Founder authorization, confirmed competitor rights, native learning-cycle execution, complete cost instrumenting and equal-physics/evaluation contracts. All numbers above are theoretical schedule counts, not measured compute-cost or performance claims.
